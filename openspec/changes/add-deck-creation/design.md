# Design

## Context

После этапа 4: `App` держит `AppState` из четырёх экранов (`decks | deck | study | results`) без роутера. Пачка (`Deck`) хранится в таблице `decks` целиком, вместе с массивом `cards`; незавершённый проход — в `activeSessions` с ключом `deckId`; ответы — в `answerLog` по `deckId` и `cardId`. Схема Dexie — `version(2)`. id карточек уже уникальны глобально (`travel-1…`, `createId()`), поэтому лог переживает перенос карточек в отдельную таблицу. `restoreSession(saved, deck)` выкидывает из очереди карточки, которых нет в пачке, и считает `totalCards` по пачке. `DeckListScreen` показывает «осталось N» прямо по `saved.session.queue.length`. Список читает пачки `toArray()` — в порядке ключа, т. е. случайных hex-id. Встроенная пачка пишется в `on('populate')` один раз.

Решения с пользователем перед этапом: мок-ошибка по ключевому слову в теме; черновик не хранится, выход — с подтверждением; котёл карточек с принадлежностью к пачкам; склейка совпадающих пар; виртуальная пачка «Все карточки»; карточки без пачки не удаляются; состав прохода фиксируется при старте вместо сброса прохода.

## Goals / Non-Goals

**Goals:**
- Модель данных, готовая к повторению поверх пачек: одна карточка — одна запись, принадлежность к пачкам — свойство карточки.
- Генератор за одним интерфейсом: этап 6 меняет реализацию, а не экраны (D-07).
- Логика черновика, проверки, склейки и состава прохода — чистые функции в `src/domain/` с тестами.
- Домен прохода и экраны прохода / итогов не замечают смены хранения: они по-прежнему получают `Deck` с массивом `cards`.

**Non-Goals:**
- Свой модальный диалог, анимации списка карточек, перестановка карточек.
- Реактивное обновление открытого редактора при изменении данных из другой вкладки.
- Виртуализация длинного списка во «Всех карточках».

## Decisions

### 1. Котёл: таблица `cards` с `deckIds`

```ts
// src/storage/db.ts
type StoredDeck = { id: string; title: string; frontLang: 'en'; backLang: 'ru'; createdAt: number };
type StoredCard = { id: string; front: string; back: string; deckIds: string[]; createdAt: number };

db.version(3).stores({
  decks: 'id, createdAt',
  cards: 'id, *deckIds',
}).upgrade(...)
```

- Принадлежность — массив `deckIds` на карточке с multiEntry-индексом: «карточки пачки» — `where('deckIds').equals(deckId)`. Пустой массив — карточка без пачки (во «Всех карточках»).
- Доменный `Deck` остаётся «пачкой для показа» — `{ id, title, frontLang, backLang, cards: Card[] }`; его собирает хранилище (`getDeck`, запросы экранов). Типы хранения — `StoredDeck` / `StoredCard` — живут в `src/storage/`. Так проход, итоги, лог и их тесты не меняются.
- Порядок: карточки — по `createdAt` (затем `id`), пачки — по `createdAt`. Сейчас порядок у пачек случайный (ключ — hex-id), с созданием пачек это стало бы заметно.
- Отдельная таблица связей пачка ↔ карточка — нормальнее для SQL, но в IndexedDB это лишние запросы и транзакции; массив с multiEntry-индексом — штатный путь Dexie.

Альтернатива: оставить карточки внутри пачки — одна карточка в двух пачках стала бы двумя записями с двумя расписаниями повторов.

### 2. Миграция `version(3)`

`upgrade`: для каждой пачки — её карточки пишутся в `cards` с `deckIds: [deck.id]` и `createdAt` по порядку в пачке; у пачки удаляется поле `cards` и ставится `createdAt` (по порядку чтения; встроенная пачка — первой). Незавершённым проходам дописывается `cardIds` — все карточки их пачки на момент обновления (точнее восстановить нельзя, а состав пачек до этапа 5 не менялся). `on('populate')` пишет встроенную пачку уже в новом виде — Dexie вызывает его на свежей БД сразу последней версии. Тест миграции: БД `version(2)` с пачкой и проходом открывается кодом `version(3)` без потерь.

Откат на 0.4.0 без потери данных невозможен — старый код не открывает БД версии 3 (как и на этапе 3).

### 3. Состав прохода — `cardIds` в `StudySession`

- `createSession` записывает `cardIds` — все карточки пачки на старте.
- `restoreSession(saved, deck)`: очередь и `forgotCounts` — только по карточкам, которые есть в пачке; `totalCards` — число карточек из `cardIds`, которые есть в пачке. Новые карточки в очередь не попадают и `totalCards` не увеличивают — итоги остаются точными.
- Хранилище при правке проходы не трогает: согласование — при чтении. `DeckListScreen` считает «осталось N» тоже через `restoreSession`, иначе отметка в списке и экран пачки разошлись бы после удаления карточки.

Альтернатива: сбрасывать проход при добавлении карточек — проверка нужна в каждой записи, добавляющей карточки, а для «Всех карточек» это любая генерация; снимок состава понадобится и будущей пачке «К повторению», состав которой меняется со временем.

### 4. Виртуальная пачка «Все карточки»

- Зарезервированный id `ALL_CARDS_DECK_ID = 'all'` (не совпадает ни с hex-id, ни с `starter-travel`). Строки в `decks` нет: хранилище собирает `Deck` из всех карточек, название «Все карточки».
- Благодаря общему `Deck` экран пачки, проход, `activeSessions` (ключ `'all'`) и лог (`deckId: 'all'` — контекст прохода) работают без особых случаев. Экран пачки отличается только тем, что «Изменить» открывает редактор в режиме всех карточек.
- В списке — первой строкой, отдельно от пачек, если карточек больше нуля.

### 5. Интерфейс генератора — функция с `AbortSignal`

```ts
// src/generation/generator.ts
type GeneratedDeck = { title: string; cards: Array<{ front: string; back: string }> };
type DeckGenerator = (topic: string, signal: AbortSignal) => Promise<GeneratedDeck>;

type GenerationErrorKind = 'network' | 'failed';
class GenerationError extends Error { kind: GenerationErrorKind }

export const generateDeck: DeckGenerator = mockGenerateDeck; // этап 6 меняет эту строку
```

- Функция, а не класс/сервис: одна операция, легко подменить в тестах.
- `AbortSignal` — стандартный способ отмены, на этапе 6 тот же сигнал уйдёт в `fetch`. Отменённый запрос отклоняется с `DOMException('AbortError')`, экран его игнорирует.
- Ошибка — свой класс с `kind` (union, без `enum`); любое другое исключение экран трактует как `'failed'`. Этап 6 добавит виды (код доступа, лимит) — сообщения расширяются, интерфейс нет.
- Карточки без id: id — забота приложения.

Новая папка `src/generation/` — граница с будущей серверной функцией; в `domain/` ей не место (там нет асинхронности и I/O). Структуру в `AGENTS.md` дополнить.

### 6. Мок: фиксированный набор слов, задержка, ключевые слова

- Возвращает один и тот же набор из 24 пар «кухня и еда» независимо от темы; название — тема с заглавной буквы (`trim`). Осмысленность по теме — этап 6. Повторная генерация того же набора заодно проверяет склейку.
- Задержка 1500 мс через `setTimeout`, снимается по `abort`. Задержка — параметр фабрики (`createMockGenerator({ delayMs })`), тесты идут с `0`.
- Ошибка тоже приходит после задержки (видно состояние загрузки). «ошибка» → `failed`, «сеть» → `network`, по подстроке в `toLowerCase()`.

### 7. Черновик и склейка — чистые функции в `src/domain/deckDraft.ts`

```ts
type DraftCard = { id: string; front: string; back: string };
type DeckDraft = { title: string; cards: DraftCard[] };

draftFromGenerated(generated, createCardId = createId): DeckDraft
draftFromDeck(deck): DeckDraft
validateDraft(draft, { requireTitle }): { canSave: boolean; incompleteCardIds: Set<string> }
normalizeDraft(draft): DeckDraft          // trim, без пустых карточек
isDraftChanged(draft, initial): boolean   // по normalizeDraft, а не по сырому вводу
cardKey(front, back): string              // trim + toLowerCase, ключ склейки
```

- id карточкам даём сразу при создании черновика: это стабильные `key` в React. У существующих карточек id сохраняется — исправленная карточка та же, лог к ней привязан.
- `canSave`: (если нужно) непустое название, нет карточек с одной заполненной стороной, есть хотя бы одна полная карточка.
- `isDraftChanged`: добавить и не заполнить карточку или поставить пробел в конце — не изменение, выход без вопроса.
- Склейка — функция планирования записи: по нормализованному черновику, id исходных карточек пачки и всем карточкам котла возвращает, какие карточки создать, какие обновить (текст), каким добавить или убрать `deckId`. Новая карточка (id не из исходных), чей `cardKey` совпал с существующей, заменяется существующей; совпадения внутри черновика сливаются в первую. Существующие карточки, ставшие одинаковыми после правки, не склеиваются (non-goal). Чистая функция → тесты без БД.

### 8. Хранилище

`src/storage/decks.ts` — каждая операция одна транзакция `rw`:

- `saveDeck(deckId | undefined, draft)` — новая пачка (`createdAt: Date.now()`) или правка: план склейки из решения 7 по всем карточкам котла (сотни записей — читать целиком дёшево), затем запись пачки и карточек. Карточке, убранной из пачки, удаляется `deckId` — карточка остаётся. Возвращает id пачки.
- `saveAllCards(draft)` — правка «Всех карточек»: исправленный текст, новые карточки с `deckIds: []` (со склейкой: совпавшая с существующей не создаётся), удалённые — `bulkDelete`. Подтверждение — в UI до вызова.
- `deleteDeck(deckId)` — пачка, её проход и `deckId` у карточек; карточки и лог остаются.
- Проходы при правке не трогаем (решение 3). `answerLog` не трогаем никогда.

### 9. Экраны и навигация

```ts
type AppState =
  | ... // как было
  | { screen: 'create' }
  | { screen: 'edit'; deckId: string }; // в том числе 'all'
```

- `CreateDeckScreen` (`src/screens/`) — шаги в локальном состоянии: `topic | generating | failed(kind) | draft(DeckDraft)`; тема — отдельное состояние, переживает все шаги. `AbortController` в `ref`; «Отмена» и размонтирование вызывают `abort()`. Шаг `draft` рендерит `DeckEditor`.
- `EditDeckScreen` — читает пачку (или все карточки) один раз и рендерит `DeckEditor` с `key={deckId}`; редактор берёт начальный черновик один раз.
- `DeckEditor` (`src/components/`) — два режима: **пачка** (`mode: 'deck'`: поле названия, «×» — убрать из пачки, «Удалить пачку» у сохранённой) и **все карточки** (`mode: 'all'`: без названия, «×» — удалить навсегда). Новая пачка и сохранённая — один режим: редактор отличает их по наличию исходной пачки (заголовок «Новая пачка» / «Правка пачки», выход из черновика — всегда с вопросом, без «Удалить пачку»). Сам в БД не пишет — колбэки `onSave(draft)`, `onCancel()`, `onDelete?()`.
- После сохранения — экран пачки (`deckId` или `'all'`); после удаления пачки — список.
- `DeckListScreen`: «Все карточки» первой строкой, пачки по `createdAt`, «Создать пачку» под списком, подсказка при отсутствии пачек. `DeckScreen`: «Изменить» в шапке справа, напротив «← Пачки».

### 10. Подтверждения — `window.confirm`

«Выйти без сохранения?», «Удалить пачку „…“? Карточки останутся во «Всех карточках»», «Удалить навсегда N карточек? Они пропадут из всех пачек» — системный `confirm`. В standalone-PWA на iOS он показывает нативный алерт; своя модалка не нужна.

Альтернатива: свой диалог — больше кода ради того же результата; вернёмся, если `confirm` поведёт себя плохо на iPhone.

### 11. Вёрстка редактора

- Шапка закреплена (`position: sticky`): «Отмена» слева, «Сохранить» справа — привычно для iOS; заголовок «Новая пачка» / «Правка пачки» / «Все карточки».
- Поле названия (в режиме пачки), затем карточки: у карточки два поля друг под другом (EN, RU) и кнопка «×» справа — две колонки на узком экране обрезали бы длинные переводы. Незавершённая карточка — рамка `--danger` и подпись «Заполните обе стороны».
- Поля — `font-size: 16px` и больше, иначе Safari на iPhone масштабирует страницу при фокусе. У английского поля `autocapitalize="off"`, `lang="en"`; у русского `lang="ru"`.
- «Добавить карточку» под списком; новая карточка получает фокус в английском поле.
- «Удалить пачку» — внизу, текстовой кнопкой цвета `--danger`, только для сохранённой пачки.
- Состояния создания (загрузка, ошибки) — через существующий `StatusMessage`, расширенный необязательными кнопками под текстом.

## Risks / Trade-offs

- [Миграция `version(3)` на установленном iPhone портит данные] → тест миграции с БД версии 2; проверка обновления превью на iPhone до релиза.
- [Правка карточки в одной пачке неожиданно меняет её в другой] → это смысл котла (опечатка исправляется один раз); другой смысл слова — другая карточка: склейка только по паре «слово + перевод».
- [Карточки удалённых пачек копятся во «Всех карточках»] → осознанно: данные не теряются молча; чистка — «×» в редакторе всех карточек. Пачка «Без пачки» — в ideas.md.
- [Редактор «Всех карточек» на сотни карточек] → сотни полей React держит без виртуализации; станет заметно — поиск / виртуализация отдельной задачей.
- [Мок попадает в продакшен-сборку на Vercel] → ожидаемо до этапа 6; ключевые слова безвредны.
- [Подстрока «сеть» срабатывает на теме «социальные сети»] → только в моке; уйдёт на этапе 6.
- [`window.confirm` на iOS выглядит системно] → приемлемо для простого UI; при проблемах — свой диалог.
- [Черновик теряется при выгрузке PWA из памяти] → выбрано пользователем: генерация дешёвая.
- [Записи лога удалённых карточек остаются «сиротами»] → осознанно: фильтруются при чтении.
- [Клавиатура iPhone перекрывает поле внизу списка] → Safari сам прокручивает к полю в фокусе; закреплённая шапка остаётся видна.

## Migration Plan

1. `version(3)` с `upgrade` (решение 2) и тестом миграции из `version(2)`.
2. Проверка на iPhone: приложение, установленное с превью `develop` до пуша этапа (сейчас там 0.4), с незавершённым проходом получает новую версию — пачка и «Продолжить» на месте.
3. Откат: на 0.4.0 без потери данных невозможен; при проблеме — исправление вперёд.
